# Greenplate — multi-user nutrition & smart pantry

Greenplate is a responsive HTML/CSS/vanilla-JavaScript app served by Express. Accounts use MongoDB-backed sessions, passwords are hashed with bcrypt, and each account's profile/meal/pantry state is stored in a separate MongoDB document.

## What is included

- Existing Greenplate interface and food scanner retained.
- Email/password sign-up and sign-in.
- Password hashing with bcrypt.
- HttpOnly, SameSite session cookie stored server-side in MongoDB; secure cookies when `NODE_ENV=production`.
- Authenticated `/api/state` endpoints scoped to the signed-in user's MongoDB ObjectId.
- Input-size limits, Helmet security headers, unique email index, and rate limits on login/registration.
- Per-user local browser cache as a fallback. The server is the shared source of truth when available.

## Run locally

Requirements: Node.js 18+ and MongoDB running locally, or a MongoDB Atlas database.

1. Open this project folder in VS Code.
2. Open Terminal → New Terminal in this folder (the folder containing `package.json`).
3. Install dependencies:
   ```bash
   npm install
   ```
4. Copy the example environment file:
   ```bash
   cp .env.example .env
   ```
   On Windows PowerShell, use `Copy-Item .env.example .env` instead. Keep `.env` private.
5. If using local MongoDB, the default URI should work. For Atlas, replace `MONGODB_URI` in `.env` with the Atlas connection string. Keep your database password out of GitHub.
6. Start the server:
   ```bash
   npm start
   ```
7. Open `http://localhost:3000`. Create an account and complete your profile.
8. Check `http://localhost:3000/api/health`; it should report `"database":"connected"`.

## Deploy on Render + MongoDB Atlas

### A. Prepare MongoDB Atlas

1. Create an Atlas project and free cluster (if available for your region/account).
2. Create a database user with a strong password.
3. Configure Atlas Network Access so the Render service can reach the cluster. For a demo, `0.0.0.0/0` allows access from any IP and is less restrictive; use it only with a strong database user password and never expose the URI. Prefer a tighter network policy if your Atlas plan/network setup supports it.
4. Copy the connection string. Replace the password placeholder with the database user's password; URL-encode special characters in the password.

### B. Push the updated project to GitHub

This project uses a **root-level** layout: `index.html`, `server.js`, and `package.json` are in the same folder. Do not set a Render root directory of `backend`.

If the GitHub repository already contains the old version, easiest safe route:

1. Download/extract this updated ZIP.
2. In your existing GitHub repository, use **Add file → Upload files**.
3. Upload/replace the root-level `index.html`, `server.js`, `package.json`, `README.md`, `.gitignore`, and `.env.example` from this folder. Do not upload a real `.env` file or `node_modules`.
4. Commit the changes.

Alternatively, use Git from the project folder. Review `git status` before committing and make sure `.env` is not included.

### C. Create the Render web service

1. Sign in at https://render.com/ and choose **New → Web Service**.
2. Connect GitHub and select your Greenplate repository.
3. Set:
   - **Root Directory:** leave blank (repository root)
   - **Runtime:** Node
   - **Build Command:** `npm install`
   - **Start Command:** `npm start`
4. Add Environment Variables in Render:
   - `NODE_ENV` = `production`
   - `MONGODB_URI` = your Atlas connection string
   - `MONGODB_DB` = `greenplate`
   - `SESSION_SECRET` = a unique random string at least 32 characters long. Generate one locally with `node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"`; do not commit it.
5. Click **Create Web Service** and wait for the deployment to finish.
6. Open the Render `onrender.com` URL. Create a test account, save profile/pantry data, refresh, and confirm it persists.
7. Check `<your-render-url>/api/health`; it should show `"database":"connected"`.
8. Test with a second account (different email) and confirm it does not see the first account's profile or pantry.

## Important limitations and production checklist

- This is a small starter app, not a security-audited production service. Before broad public launch, add email verification/password reset, account deletion/export, stronger abuse protection, monitoring, backups, and a privacy policy. Use a reputable managed database and restrict access.
- The current browser cache is namespaced per account, but server state is the shared source of truth across devices. Existing pre-login `greenplate-state` browser data is intentionally **not auto-imported** into the first account, to avoid accidentally copying one person's data into another account.
- Meal ideas are rule-based estimates, not generated by a connected AI service. Barcode lookup uses Open Food Facts when a packaged product is in its catalog; loose-produce AI photo recognition is not enabled.
- Camera scanning needs HTTPS (Render provides HTTPS) and browser camera permission.
- Never commit `.env`, passwords, Atlas connection strings, or `SESSION_SECRET` to GitHub.
